# Changes for users of geometry3Sharp 1.0.324

This fork keeps the public API of upstream geometry3Sharp 1.0.324 (commit `ece3364`), but a number of existing
methods give different results: almost all of them are bug fixes. This page lists the changes that existing
code can notice. New classes are not listed (see the README and [OPERATIONS.md](OPERATIONS.md)).

## Results that change

| Class / member | 1.0.324 | Now |
|---|---|---|
| `MarchingCubesPro.GenerateContinuation`, serial and parallel | the visited-cell grid omitted the inclusive upper cell on each axis: cells could alias the next row and silently skip whole components, or throw `IndexOutOfRangeException` (aggregated in parallel); the corner cache also omitted the far corners of that layer | visited cells and cached corners cover the complete inclusive grid. Upper-layer components are retained, including after reuse or a call to `Generate`. Legacy modes ignore seeds whose cell indices lie outside the continuation grid; `LinearEdges` retains its existing rejection of such seeds. The continuation's traversal extent is unchanged |
| `MarchingCubes.Generate`, invalid cube size or bounds | casts from NaN/infinity or oversized axis counts could give invalid dimensions, no output or wrapped exceptions | finite positive `CubeSize`, finite bound coordinates and cell counts fitting in `int` are required; invalid values throw `ArgumentException` before field evaluation. Unlike dense samplers, there is **no product-of-dimensions array limit**: large streaming grids remain accepted. `AxisAlignedBox3d.Empty` and finite inverted axes keep the upstream `max(extent, 0)` behavior (one cell per empty axis), not an exception |
| `MarchingCubes.Generate`, parallel output | vertex and triangle IDs followed thread completion order | bounded batches of slabs are evaluated in parallel and published in serial z/y/x traversal order; completed runs of a deterministic, thread-safe field have identical IDs, coordinates, triangles and `VertexHash` to serial generation. Cancellation may still return a partial mesh; `MarchingCubesPro` is not changed by this ordering fix |
| `ImplicitFieldSampler3d` constructor, invalid cell size/bounds or oversized dense grid | invalid dimensions could reach allocation or sampling | uses the same finite-positive size and representable dense-array checks as the sampling grids, throwing `ArgumentException` before allocation |
| `DSubmesh3Set.Submeshes` and `KeyToMesh` | submeshes were appended in worker completion order; repeated keys selected whichever worker finished last | submeshes follow `TriangleSetKeys` enumeration order, and the final occurrence of a repeated key supplies its mapping |
| `MeshSpatialSort.Sort` | an invalid bbox-containment comparator reordered components; relationship lists followed worker completion order and accumulated across calls | uses original `Components` order as the tie-breaker and publishes containment lists deterministically. `Solids` and cavity order may differ from upstream; `InsideOf` and `InsideSet` are cleared and rebuilt on every call |
| Parallel `MarchingCubes.Generate`, `DSubmesh3Set` construction and `MeshSpatialSort.Sort`, worker exceptions | a worker failure was normally wrapped in `AggregateException` | the shared `gParallel.ForRange` helper rethrows the original exception if there is exactly one inner exception (including failures from `Implicit.Value` or `TriangleSetF`); multiple worker exceptions remain aggregated. Serial paths keep their direct exceptions |
| `Reducer` midpoint paths at extreme coordinates | `(a + b) * 0.5` could overflow even when the midpoint was finite | halve the endpoints before adding in fast collapse, non-optimal placement, regularization and fallback. Subnormal coordinates can round differently; ordinary finite midpoints are unchanged |
| `WindingContouring` refinement margins at integer limits | bounds, cell offsets or inclusive counters could wrap to unrelated cells | range endpoints are intersected with the `int` coordinate domain before narrowing, with `long` inclusive counters; out-of-range neighbours are omitted rather than wrapped. Terrain margin handling is unchanged |
| `DMesh3.CompactInPlace()` with isolated live vertices above deletion holes | could throw while moving a nonexistent adjacency list | preserves the isolated vertices and their attributes, with the requested vertex mapping |
| `DMesh3.RebuildFromEdgeRefcounts()` and `gSerialization.Restore(DMesh3, ...)` with a reused destination | old vertex/triangle refcounts and adjacency could survive or make rebuilding throw | derived topology is reset before rebuilding from the supplied buffers; restored live IDs and attributes match a fresh destination |
| `DMeshAABBTree3.Build()` on an empty mesh | bottom-up strategies produced an invalid root and queries threw | all strategies build a valid empty leaf; queries return their existing no-hit sentinels |
| `DMeshAABBTree3.Build()` with `TopDownLeafMaxTriCount` below 2 | stack overflow | treated as 2 |
| `DMeshAABBTree3.FindNearestHitTriangle` when the ray hits several triangles at the same ray parameter (a shared edge or vertex) | the triangle found first in the traversal, whose order the box padding changed with the scale while it was absolute (about 6e-6): another id below about 1e-6 model size | the lowest id among them, as `MeshQueries.FindHitTriangle_LinearSearch`; the same at every power-of-two scale (the traversal prune is still absolute, so at ray parameters above about 1e10 with non-dyadic geometry a tie can still depend on the order, as before) |
| `IntrRay3Triangle3` (`Find`, `Intersects`), so `DMeshAABBTree3.FindNearestHitTriangle` / `FindAllHitTriangles`, `MeshQueries.FindHitTriangle_LinearSearch` and `IntersectionUtil.Intersects` | hit / no hit by rounded edge functions: a ray onto (or within rounding of) a shared edge or vertex could miss every triangle there (eg at 1e-3 and 1e-7 model size), and rays within about 1e-8 of a triangle's plane were "parallel" (no hit) | decided exactly (`Orient3d` signs of the ray's line, through the origin and origin + 2^m direction, against the closed triangle): a ray onto an edge or vertex hits every triangle there, a ray in the triangle's plane none, no parallel tolerance; the same at every 2^k scale. `RayParameter` and `TriangleBaryCoords` are the same doubles for every ray that 1.0.324 and the exact rule both hit (barycentrics of new hits clamped into the triangle); a ray within rounding of the edge of a lone or boundary triangle can change between hit and miss. Finding Q2 |
| `DMeshAABBTree3.FindNearestTriangle`, `FindNearestTriangles` and the boxes handed to `TreeTraversal.NextBoxF` / `NextBoxDF` | boxes padded by a fixed 6e-6, so under a scale by 2^k the traversal order, the winner of an exact tie between triangles (and, in sums over the tree, the order of the terms) changed: not bit-identical (the Remesher with projection, `MeshICP`, `WindingNumber` at 2^-24) | padded by 2^-40 of the larger of the mesh size and its distance from the origin, so the same answers at every 2^k scale. The winner of a tie between equally near triangles can be another valid triangle than before; the boxes of the traversal are 6e-6 tighter on a unit-size mesh (Reducer / Remesher 2.0 T5) |
| `DMeshAABBTree3.IsInside` | parity of `FindAllHitTriangles`: a ray through a vertex counted 0 to n triangles, through an edge 0 to 2, so the answer could be wrong for closed meshes | parity of the crossings of the same ray perturbed symbolically (Simulation of Simplicity): each crossing counted once, right for every closed mesh without self-intersections and every point off its surface. Still parity: for open or broken meshes use `WindingNumber`. Finding Q3 |
| `DMeshAABBTree3.TestIntersection`, `FindAllIntersections`, `FindNearestTriangles` with another tree | only checked whether the receiver mesh had changed | also reject a modified argument mesh or a never-built argument tree before traversal or the transform callback; rebuild both trees after editing their meshes |
| `OpenCylinderGenerator`, `CappedCylinderGenerator`, `ConeGenerator`, `VerticalGeneralizedCylinderGenerator` (and `Radial3DArrowGenerator`) | triangles faced inward with the default `Clockwise = false` (negative volume) | they face outward like the other generators. Drop any `ReverseOrientation()` or `Clockwise = true` that compensated for it |
| `Reducer` | boundary edges collapsed to their midpoint; plain `OptimalPoint` solve | with `PreserveBoundaryShape` (default) boundary planes are added to the quadrics (`BoundaryQuadricWeight = 100`) and boundary edges keep an endpoint; `QuadricRegularization = 1e-6`. Results differ slightly on closed meshes and noticeably along boundaries (kept exactly, coarser) |
| `Reducer.ReduceToMaxQuadricError` | the stop used float queue priorities against the double budget; constraints could change the accepted position without a budget recheck | accepts a collapse only when its final position's double quadric error is within the budget; checks the whole rounded priority bucket so upward rounding does not reject an equal-cost candidate. NaN budgets accept no collapses. Float ordering remains; post-pass `AfterRefinement` projection is outside this contract |
| `Reducer.PreventSelfIntersections` | a pre-filter with the open `AxisAlignedBox3d.Intersects` skipped triangles whose box is flat in the plane of the other's or only touches it: coplanar overlaps in an axis plane (and touches at a box face) were accepted | those collapses are refused: axis-flat regions and boxes that only touch now get the exact tests. A region of coincident or overlapping sheets freezes, as every new triangle intersects the other sheet: coincident z = 0 sheets of 6400 triangles reduced to 640 stay at 6400 (was 640), two boxes touching at a face of 1944 reduced to 194 stop at 540 (was 194). A refused collapse changes the ones after it, so the final mesh can also differ elsewhere; meshes without such boxes are unchanged. Cost: by itself 2.7 to 3.7 times on axis-flat meshes; with `TriangleTriangleFilter` in front of the exact tests (the same change) the check is faster than before on every measured mesh, with results bit-identical to the box fix alone (and to master on the measured meshes, which have no such boxes) (0.11 to 0.94 of the old time, `benchmarks/SelfIntersectionBenchmark`). The filter only answers where the exact answer is known, so the decisions are those of `ExactTriangleIntersection`. Triangles with a coordinate that is not finite are not checked (the exact tests need finite input; the open box test skipped most of them before). This also reaches `MeshRobustRepair` and `WindingContouring`, which use the option. `AxisAlignedBox3d.Intersects` itself is unchanged |
| `Reducer.PreventFoldOver` (new, default on) | a collapse was checked only against the current normals of its triangles (90 degrees each), so chains of collapses folded surfaces over: on a noisy 40 x 40 terrain reduced to 20 %, 1 to 4 triangles turned down and vertical walls stood along the border (meshoptimizer issue 346) | a new triangle must also have a positive dot with the area-weighted input normals its corners have absorbed (summed on collapse; taken at the start of each reduction), and a dot above `BoundaryTriangleMinNormalDot = 0.7` if it has two boundary edges (the walls; read from the current mesh); where those normals nearly cancel (`ReferenceNormalMinLength = 0.25` of their summed lengths: creases, the rim of a thin plate, boxes touching at a face) only the old check applies. On 72 noisy terrains: 20 folds and 110 walls before, 7 and 0 after (the 7: interior slivers that stand nearly vertical within 90 degrees of the input normals, mostly at noise +-0.8); box, cylinder, sphere, thin rod, thin plate and open bands reach the same targets. Results change wherever the check rejects a collapse; `PreventFoldOver = false` gives the old ones. Time (the check in the same pass over the one-rings as the flip test): 1.00-1.14 x without `MaxDeviation`, 1.01-1.02 x with it; the bumpy sphere of `benchmarks/ReducerBenchmark` is reduced bit for bit as before, the terrain differs (7 folds at 20 % before, 0 after; `folds`). This also reaches `MeshRobustRepair.SimplifyWithin` (alpha wrap) and `WindingContouring` (closed meshes, already with `EdgeFlipTolerance` cos 60 degrees) and `g3cli reduce` |
| `Reducer` on a mesh with bowtie vertices (fans of triangles meeting only at a vertex, eg two cones tip to tip) | a collapse could remove the bowtie vertex or move it: the fans were joined (an edge from one cone to the other, the lower cone's apex dragged up), and reduced hard, duplicate triangles and a cone of zero volume | a bowtie vertex is kept in place and never removed (an edge between two bowtie vertices is not collapsed); meshes without bowtie vertices are unchanged (`ReducerIssueCasesTests.TwoConesJoinedAtTheTip_*`) |
| `Reducer.ReduceToEdgeLength(NaN)`, `FastCollapsePass(NaN)` | collapsed every edge it could | accept no collapses; the mesh stays as it is |
| `MeshIsoCurves.Compute` with a NaN field value | `SingleLerp` and `LerpSteps`: NaN positions in `Graph`; `Bisection`: finite, but a spurious curve along the border of the NaN | the triangle adds nothing in every mode, so a NaN iso value gives an empty `Graph` and `SplitAtIsoCrossings` splits nothing. `Compute()` has no status: an empty `Graph` also means no crossing |
| `MeshIsoCurves.Compute` with +infinity and -infinity in one triangle | `SingleLerp` and `LerpSteps`: NaN positions in `Graph` | those modes add nothing for the triangle (same remark on the status). `Bisection` is unchanged: it uses only the signs and finds the jump |
| `MeshIsoCurves.Compute` with one infinite value in a triangle | -infinity gave NaN positions in `Graph` with `SingleLerp` and `LerpSteps`; a 0 next to an infinity took the path for three crossings (a vertex without an edge); `LerpSteps` passed on a NaN met between the vertices | the crossing is at the finite vertex of the edge (`Bisection` as before finds the jump); a 0 next to an infinity gives the edge of a 0 with finite values; `LerpSteps` stops at a NaN |
| `MeshIsoCurves.SplitAtIsoCrossings` with a crossing exactly at a vertex of the edge | split the edge, with an edge of length 0 and triangles without area | leaves that edge alone |
| `TerrainSafetyLines.Compute` (a class of this fork, listed as it changed since its first release) | very small finite `ExcessTolerance`, `Tolerance` or `EdgeLength`, or very long sources: an `OverflowException`, an out-of-memory error or a near hang on .NET, one sample per segment on .NET Framework; a triangle vertex of the terrain that is not finite: splits until out of memory | `Compute` returns false with no outputs on both runtimes, for such a vertex and above the constants `MaxCertifySteps`, `MaxSourcePoints` and `MaxRefinedTriangles`. Results below them are unchanged, bit for bit |
| `AxisAlignedBox3i.IndicesInclusive`, `AxisAlignedBox2i.IndicesInclusive` with `Max` at `int.MaxValue` on an axis | never ended (the counter wrapped around) | end after the last cell; other ranges are unchanged |
| `Reducer` subclasses | quadrics in absolute coordinates | `vertQuadrics` and the quadrics passed to `OnEdgeCollapse` are relative to `quadricOrigin` (the mesh bounds center); use `plane_quadric` / `evaluate` |
| `IntrTriangle3Triangle3` (`Test()`, `Intersects()`, `Find()`; also `DMeshAABBTree3.TestIntersection` / `FindAllIntersections`, `MeshQueries.TrianglesIntersection`) on coplanar, nearly parallel (sine of the angle below 1e-4) and sliver triangles, and triangles within 1e-8 of another's plane | floating-point separating axes and 2D clipping with a fixed epsilon: touching coplanar triangles missed (eg 1317 of 20000 half-integer lattice pairs, 11079 of 40000 coplanar pairs in oblique planes), disjoint ones reported (618 of those 40000; a pair within 1e-8 of a plane as overlapping), `Find()` true without contact points (9398 of 20000 coplanar slivers) or false where `Test()` was true | decided exactly (`ExactTriangleIntersection`, closed triangles), the same in all three; `Find()` gives the contact from exactly decided pieces with only the crossing points rounded: at least one point whenever they intersect, the polygon for exactly coplanar ones (with `ReportCoplanarIntersection`, as before), the segment or point otherwise; so nearly coincident faces that are not exactly coplanar now give their crossing segment also without `ReportCoplanarIntersection` (`FindAllIntersections` reports it). Non-finite coordinates: no intersection. Costs 4-40x more on these pairs, about 0.1-0.2 µs more per pair in general position (`benchmarks/PredicateComparison -- triangles`). Pairs at small angles above that band keep the floating-point path |
| `DMesh3.GetBounds()`, `CachedBounds`, `DGraph2/3.GetBounds()` of an empty mesh / graph | a zero-size box at the origin | `AxisAlignedBox3d.Empty` (negative extents). `MeshSignedDistanceGrid`, `MeshWindingNumberGrid`, `MeshScalarSamplingGrid` and `CachingMeshSDF` throw an `ArgumentException` on an empty mesh |
| `DMesh3.AllocateTriangleGroup()` | skipped an id (6 on a mesh whose groups are 0..4) | returns the next unused id (5) |
| `MeshTransforms.Rotate(mesh, origin, Quaternionf)` | positions only | also rotates vertex normals, in double precision |
| `MeshMeasurements.MassProperties(..., bodyCoords)` | `bodyCoords` was ignored | honored |
| `Remesher` flips | only to improve the valence | also an edge of a degenerate (zero-area) triangle, when both new triangles are proper and face the same way (removes slivers that no collapse can remove, eg between pinned corners or along feature curves) |

## Performance

`DMeshAABBTree3` stores its boxes in double precision (correct far from the origin, about 5-15% slower nearest
triangle queries, twice the box memory). `Reducer` is about 5-10% slower (boundary quadrics, regularized
solve). `FastWindingNumber` is a bit faster.
